# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, single-page tool that projects the future value of a group of investments. Each holding is entered as its **value today** (principal plus any historical compounding already baked in), an **annualised return**, and an optional recurring monthly **deposit**. That value-today figure is projected straight forward; there is no historical holding period. No backend, no persistence; loads with an illustrative example. It is explicitly not financial advice — it extrapolates, and the UI says so.

The app runs in one of **two top-level modes**, a data-carrying `calc::Plan` chosen by a mode switch (a radio group styled as a segmented control) that reconfigures the whole page:

- **Deposits ("Building it up")** — grow every holding from its value today, adding each row's monthly deposit, over the horizon. The classic accumulation.
- **Drawdown ("Drawing it down")** — grow for `horizon_months` (the same horizon control), *then* spend the **projected** pot down over a second `drawdown_months` phase, taking a single **portfolio-level** monthly `withdrawal` that is apportioned across the holdings **pro-rata by current value and rebalanced every month**. Monthly deposits stop at the handover; the only drawdown-phase cash flow is that withdrawal. The pot drawn down is the value *at the end of accumulation* (`series[horizon_months]` = `CalcOutput::handover_total`), never today's value.

`calculate` produces **one continuous month-by-month series across both phases**, so the UI never stitches two projections or computes the handover itself. The withdrawal is capped at the whole pot each month; because the split is monthly pro-rata, every holding empties in the *same* month, so `CalcOutput::depletion_month` (an **absolute** index into `series`) is the portfolio's single depletion point — there is no per-holding depletion field. A zero/blank withdrawal is a legal flat drawdown (just a longer accumulation).

Note on the growth figure: `growth` is returns-only — `projected_total − current_total − (contributed_total − withdrawn_total)`, i.e. net of the cash you moved in *and* adding back what you withdrew, so neither future deposits nor withdrawals are reported as investment performance; `growth_pct` measures that gain against deployed capital, reported as `deployed` (`current_total + contributed_total`, deposits only — withdrawals don't change what was put in) so the UI can state the denominator instead of showing a bare percentage. This identity holds unchanged across the handover.

Several output fields exist purely so the figures **reconcile on screen**, and should not be dropped as redundant: `InvestmentResult::contributed` (a row showing `£10,000 → £53,881.86 at +7.00%` is nonsense without the `£24,000` of deposits that bridge it), `InvestmentResult::withdrawn` and `InvestmentResult::handover_value` (the same, for a drawn-down row — the drawdown is measured against the handover pot, not today's value), and `CalcOutput::deployed` (as above).

**The whole app is Rust compiled to WebAssembly** — a pure calculation library plus a [Leptos](https://leptos.dev) client-side UI. There is no JavaScript.

## Architecture

A **virtual Cargo workspace** (the root `Cargo.toml` is `[workspace]`-only — no root package) with four named member crates. Two are the projection, two are the tax model:

```
        taxkit          traits + neutral types. No jurisdiction anywhere.
       /      \
   calc        uk-tax   projection engine  |  UK rules and rates
       \      /
         app            picks the system; renders whatever it advertises
```

- **`taxkit/` (library)** — the abstraction between a projection and the tax system it works with. Defines `TaxSystem` (a catalogue of `AccountKind`s, a set of `Region`s, an `as_of` date and a `staleness` judgement) and `TaxSession` (one projection's ledger, answering `marginal_keep` and `draw`), plus `SimpleDate`, `Pot`, `Draw`, `StopAt`, `TaxError`. **Nothing in it names a country, currency, account type or allowance** — if a reviewer can tell which jurisdiction it is for, it is wrong. It also ships `ladder`, a shared closed-form walker for piecewise-rate schedules (a *helper*, not part of the contract), and a `mock` feature: a fictional flat-rate tax system that `calc` tests against. The mock is not a convenience — an abstraction designed against one implementation quietly grows that implementation's shape, and it is the second implementation that stops it.
- **`uk-tax/` (library)** — the UK, implementing those traits. Split deliberately in two: `tables.rs` is **data** (rates, thresholds, allowances and the account catalogue, every threshold a whole-pound `i64` and every rate basis points `u32`, so an update is unambiguously a change of integer literals) and `engine.rs` is **mechanism** (how those figures become a ladder, and how a withdrawal is priced against it). A rate change touches only `tables.rs`; a change to the tax *system* — a new band structure, a different taper, a new kind of account — touches `engine.rs`. Models income tax across all four UK jurisdictions including the withdrawn personal allowance, capital gains with the annual exempt amount and both rates, phased tax-free pension cash against the lifetime lump sum allowance, and the normal minimum pension age. Does not model dividend or savings income, capital losses, chargeable event gains, or inheritance tax.
- **`calc/` (library)** — every financial calculation, in exact base-10 `Decimal` (`rust_decimal`). Pure: no UI, no WASM/`web_sys`, no floating point. Exposes typed `calculate(&CalcInput) -> Result<CalcOutput, CalcError>` plus the `Unit`/`Plan`/input/output types, and the goal-seek `solve(&CalcInput, &Goal) -> Result<Solution, CalcError>`. `Goal` has **four variants, two per mode**: the deposits questions `MonthlyTopUp { target }` and `TimeToTarget { target }` carry a target string; the drawdown questions `MaxWithdrawal` and `TimeToDeplete` carry **nothing** — the drawdown period and the monthly withdrawal they reason about are already in the `CalcInput`. Every goal is measured against the whole portfolio (there is no `Scope`). `MaxWithdrawal` bisects for the largest draw that reaches exactly £0 at the end of the drawdown period; `TimeToDeplete` reports `Solution::Depletes(m)` where **`m` is months of *drawdown*, not months from today** (`depletion_month` is absolute; the two differ by `horizon_months`). `calc` also owns *input parsing*: the public `parse_number` accepts numbers the way users type them (`1,234.56`, `£1,234`, `7 %`), so the UI never pre-cleans a string. `Plan::Drawdown` also carries a `Strategy` — how the monthly withdrawal is apportioned — now a struct of two orthogonal axes, `Strategy { order: Order, stop: Limit }`, with five named constructors for the strategies the UI offers (`Strategy::pro_rata`/`ordered`/`cheapest_first`/`preserve_growth`/`rate_capped`). `Order` is `ProRata | ByKind(ids) | ByReturn | ByMarginalCost`; `Limit` is `Requirement | NextRung | RateCap(percent)`, consulted only by `ByMarginalCost` (the static orders always draw to `Requirement`). Every order except `ProRata` treats the withdrawal as **net**; pro-rata takes it **gross** and opens no tax session, which is what keeps it byte-identical with and without a `TaxContext`. All orders run through the one static split (`static_month`, pro-rata being a single all-holdings group) or the one greedy pass (`greedy_month`, for `ByMarginalCost`) — there is no third mechanism. Ordering is expressed over **opaque account-kind ids** from whatever `TaxSystem` is supplied, so `calc` never learns what an account is. This is the single source of numeric truth and is natively unit-testable. The month loop is **month-major** (all holdings advance together) because the drawdown split needs every holding's balance at once; that split's rounding residue lands on the last member of each group it apportions, so `Σ per-row withdrawn == withdrawn_total` stays exact.
- **`app/` (library + a thin binary)** — the Leptos UI, and the web entry it owns (`app/index.html`, `app/styles.css`). It is a **lib crate** (`app/src/lib.rs` declares the modules and re-exports `App`) plus a five-line `app/src/main.rs` bin that only `mount_to_body`s it; the split exists so the headless-browser suite in `app/tests/ui.rs` can `use app::App` and mount the real component. Split into modules: `app/src/app.rs` (the top-level `App` component, the mode switch, and the `web_sys` clipboard/history glue), `app/src/convert.rs` (form strings → `calc::CalcInput` via a `FormInput` bundle, including the `<select>`→enum maps and `plan_from`), `app/src/outcome.rs` (a recomputation's result plus the error→control mapping), `app/src/goal.rs` (goal form strings → `calc::Goal`, mode-aware; and `calc::Solution` → the answer sentence), `app/src/share.rs` (the fragment codec that packs/unpacks the whole form for a shareable link as base64url-encoded JSON), `app/src/model.rs` (the reactive `Row` and its DOM helpers), `app/src/summary.rs`/`app/src/results.rs` (the two output panels), `app/src/panel.rs` (the last-good/`.stale` shell both panels share), `app/src/strategy.rs` (the side-by-side comparison of withdrawal orders), `app/src/freshness.rs` (whether the tax figures are still current — the only clock read in the app), `app/src/format.rs` (`Decimal`→display-string formatting), and `app/src/chart.rs` (the hand-built SVG). It owns the reactive form state and **only formats** the `Decimal`s that `calc` returns. It must not compute, derive, round, or validate any number — that all belongs in `calc`. The one non-`calc` numeric code is `chart.rs`'s pixel geometry (cosmetic `f64`, never a reported figure). `convert.rs`, `outcome.rs`, `goal.rs`, `share.rs`, `format.rs` and `chart.rs` are pure and carry their own `#[cfg(test)] mod tests` (as does `results.rs`'s extracted `month_at_fraction`). `app.rs`'s clipboard/history glue (`share.rs` is the pure part) is the only genuinely `web_sys`-bound code; the whole reactive/DOM layer (`app.rs`, `summary.rs`, `results.rs`, `panel.rs`, `model.rs`) is covered by the browser suite in `app/tests/ui.rs`.

The load-bearing rule: **numbers live in `calc`, presentation lives in `app`.** Because both are Rust they share types directly — there is no JSON/string boundary between them (a deliberate change from the earlier wasm-bindgen design).

The second load-bearing rule: **jurisdiction lives in `uk-tax`.** `calc` and `app` must never name an account type, an allowance or a country. The test for which side of that line something falls on is *would this change if a legislature changed the tax system?* — if yes, it belongs in the implementation crate. `calc` depends on `taxkit` only, never on `uk-tax`; `app` names the UK on exactly one line. Enforced by grep, see **Build & run**.

The third load-bearing rule: **jurisdiction crates are named `{iso-3166-alpha-2}-tax`** — `uk-tax`, and `de-tax` for Germany. Cargo maps the hyphenated *package* name to an underscored *lib target*, so the directory and manifest read `uk-tax` while Rust code says `uk_tax::UK`; `cargo`/CI use the hyphen, source greps use the underscore. `taxkit` deliberately does **not** follow the pattern: it is the neutral contract, not a jurisdiction, and an `xx-tax` name would imply otherwise.


## What "best" means, and what was rejected

The drawdown feature answers "what is the best way to take this money out?". "Least tax" is the obvious reading and the wrong one to ship alone: optimising it hard is worse on every other axis — the lowest-tax order will drain a tax-free account early and leave a wholly taxable one to come out at the top rate.

So `.strategy-compare` reports **several axes and ranks none of them**: total tax, net income delivered, how long it lasts, what is left at the end, allowance left unclaimed, and accounts touched per year. **This is a constraint, not a styling choice.** A single "best" figure would read as a recommendation however it were captioned, whereas a table of consequences with no winner leaves the judgement with the reader — which is the right posture for a tool that disclaims advice. No ranking, no sorting by outcome, no "recommended" badge, no highlighted cell, no "you would save £X". A UI test asserts the absence of those words.

Strategy labels stay descriptive ("Lowest tax this month", "Longest-lasting pot"), and the ordered one composes its label from the account names in the order itself, so even that string is generated rather than written.

`unused_allowance_total` is the *show-your-working* column: it is what explains why one order beats another, and it turns the table from a scoreboard into an explanation.

**Deliberately rejected, so these do not get re-proposed:**

| Rejected objective | Why not |
| --- | --- |
| Minimise inheritance tax / maximise the estate | The most tempting one, and topical. But it needs a death-date input and a second ruleset (nil-rate bands and their taper, spousal exemption), and it is the closest of any option to actual estate-planning advice. The "left at the end" column gives the raw material without the modelling or the framing risk. |
| Robustness to sequence-of-returns risk | The honest answer for a real retiree, and flatly incompatible with this app: it needs per-holding volatility and a Monte Carlo engine, where the core is exact-`Decimal`, single-rate and deterministic. Determinism is also what makes shared links reproducible. A different application, not a strategy. |
| Smooth real-terms income | The app models no inflation anywhere, so "£3,000 a month in today's money" has nothing to bite on. The threshold-uprating control is the minimum honest acknowledgement of the frozen-threshold problem; a real-terms mode is its own feature. |
| Preserve flexibility / optionality | Real, and not quantifiable without inventing a scoring function nobody would trust. |
| Protect means-tested benefits or care-cost thresholds | Squarely individual financial advice, and far outside an entertainment tool. |
| A true lifetime-tax optimum | Not a rejected objective but a method this cannot afford: minimising tax over thirty years is a dynamic program over the ledger state, not a greedy. `CheapestFirst` is myopic by construction and named so nobody mistakes it. |
## Reactive data flow (Leptos)

- Each investment row is a `Row` of per-field `RwSignal<String>`s (name/value/rate/contribution — so typing in one cell doesn't disturb others); `rows` is an `RwSignal<Vec<Row>>`. The mode and the drawdown controls are their own signals on `App`: `plan_kind` (`"deposits"`/`"drawdown"`), `drawdown_value`, `drawdown_unit`, `withdrawal`.
- A single `create_memo` (`outcome`) reads the form through `build_current` (which assembles a `convert::FormInput` and calls `build_input`) and runs `calculate`. Reading the signals inside the memo is what makes the projection recompute on any edit; the memo caches so `calculate` runs once even though several readers want it (the error line, each control's invalid flag, and the `displayed`/`stale` memos). `FormInput` deliberately excludes the goal fields, so typing a goal target does **not** re-run `calculate`.
- Blank rows (empty value today, rate, AND contribution) are filtered out before calling `calculate`. **This breaks the index correspondence** between `CalcInput::investments` and the rows on screen, so the memo records a parallel `row_ids: Vec<usize>` in its `Outcome`; that is what lets a `CalcError`'s index be mapped back to the right `Row`.
- `calculate` never panics; invalid input comes back as `Err(CalcError)` carrying a `message` and an optional `field` (`Field::Investment { index, part }`, `Field::Horizon`, `Field::Drawdown`, or `Field::Withdrawal`). The UI shows the message in `.error-msg` *and* marks the named control with `aria-invalid` + `aria-describedby` + `.field-invalid` (`outcome::flags_field(Field::…)` for the form-level controls, `outcome::flags(row_id, part)` for a per-row investment field).
- The **mode switch** is a radio group, not an ARIA tablist: the holdings editor is shared between modes and stays put, so there is no tabpanel to control. The growth period is the *same* `#horizon-value` input node in both modes (only the surrounding words change) — it must never live inside the mode-switched closure, or switching mode rebuilds the node and takes focus/caret with it. The drawdown period and withdrawal rows *are* conditional (`is_drawdown().then(...)`), and their `bind_value` refs are created **inside** that block so a fresh binding effect applies the seeded value when it mounts.
- Both output panels render `displayed`, a memo that holds the **last good** `CalcOutput` through a transient error, rather than blanking. That shell lives once in `panel::stale_body`: it keys the panel body on `displayed` alone and binds the separate `stale` memo to `.stale` + `aria-busy` as *reactive attributes*, so entering an error dims the figures without rebuilding the panel (a rebuild would regenerate the chart and take the scrubber's month and keyboard focus with it). It only falls back to the empty state when there are genuinely no rows.
- The error is announced through a debounced sr-only `role="status"` region, not by making `.error-msg` itself live — recomputation happens on every keystroke, and a live region there talks over the user.
- The goal-seek answer is a **separate** memo (`solution`), not part of `outcome`, on purpose: a goal that can't be met ("no top-up reaches £X in this time") is not an *input* error, so it must never set `stale` or dim the projection panels, and it must not surface through the `.error-msg`/`aria-invalid` path. It renders as its own `.goal-result` line, holding the answer sentence *or* the reason it failed (`goal::describe` maps `Ok`/`Err` alike to text). The available questions depend on the mode: `GoalKind::parse(kind, plan)` resolves the kind `<select>`'s value **within the active mode**, so a value left over from the other mode falls back to that mode's default. The two modes render **two separate `<select>` elements with static option sets**, showing only the current mode's — never one select whose options swap (which the browser resets to its first entry when the selected option is destroyed). The deposits goals need a target box (inert when blank); `MaxWithdrawal` is always live in drawdown mode; `TimeToDeplete` is inert when the withdrawal box is blank. `describe` names the growth-period `horizon_label` for a top-up answer and the drawdown-period label for the two drawdown answers, both read off `CalcOutput` via `outcome` so numbers stay in `calc`.
- Removing a row goes through `remove_row`, which also **moves focus** (see Accessibility). `Row` therefore carries its own `remove_btn: NodeRef<html::Button>`, created in `new_row` rather than inside the `For` body, so a *sibling* row's handler can reach it.

## Page structure

Three panels inside `.layout`:

| Panel | Heading | Holds |
| --- | --- | --- |
| `.panel-summary` | "Projection" | The stat cards — three to six of them, depending on mode and whether there are deposits/withdrawals. `grid-column: 1 / -1` on desktop — full width above the other two |
| `.panel` | "Your investments" | The row editor, the `.periods` block, and the goal controls |
| `.panel.results` | "Breakdown" | The chart (with scrubber) and the per-holding table |

Above all three sits the full-width `.mode-switch` (a `<fieldset>` with `grid-column: 1 / -1`), so it reads as switching the whole page context.

The summary is hoisted out of the results column deliberately: the form is inherently shorter than the results, and side by side that left a ragged hole in the page. The lower two panels then `align-items: stretch` to equal height, and `.periods` takes `margin-top: auto` to spend the form's spare height rather than leave a gap. The two columns are **evenly split** (`1fr 1fr`): the form's own four inputs are sized to fit the narrower track, while the breakdown has to hold a seven-column money table. The rate track carries a px floor (`minmax(78px, 1fr)`) rather than a bare share: the `%` adornment and input padding cost a fixed ~32px, which on a pure share left 28px of visible text at 960px — narrower than `7.25`.

Inside the summary panel the cards are a **flex row, not a grid**, because the card count varies: the headline takes `flex-basis: 100%` so it owns the top row, and the two-to-five supporting cards share the row beneath it through `flex-grow`. A grid cannot do this — the headline spans every track, so `auto-fit` never sees an empty track to collapse, and the supporting row keeps its full track count regardless of how many cards turned up (five cards sat in seven tracks, with the difference left as dead space at the right). The headline is on its own row rather than merely wider because its money string runs roughly twice the length of the others, and because any shared row eventually spills one card onto a second line alone. Between 620px and 960px there is room for four of the five supporting cards but not the fifth, and `flex-grow` inflates that orphan to the whole width of its row, so that band alone pins them to thirds — but **only in the six-card case**, selected by counting siblings (`.stat-accent:nth-last-child(6) ~ .stat`, the headline always being the first child). Applied to every `.stat` instead, the thirds rule re-creates the very orphan it exists to remove: with four supporting cards the 160px basis already fits all four on one row above ~766px, and thirds wrap them 3 + 1.

## Accessibility conventions

These are load-bearing and easy to regress silently — a change that "looks fine" can still break them.

- **Errors name a control, not just a problem.** `CalcError::field` drives `aria-invalid`, `aria-describedby=ERROR_ID` and `.field-invalid` on the offending input. A new error site in `calc` must pick a `Field`, or the message strands itself at the foot of the form again.
- **Never put a live region on something a memo rewrites per keystroke.** The visible `.error-msg` is inert; announcement goes through the separate debounced (`ANNOUNCE_DELAY`) sr-only `role="status"`. `role="alert"` here interrupts a screen reader mid-word on every character typed.
- **Destructive controls move focus.** `remove_row` focuses the successor row's remove button, or `+ Add investment` when the list empties; otherwise focus falls to `<body>` and a keyboard user restarts at the top of the page. No `request_animation_frame` is needed because the `For` is keyed by `Row::id`, so surviving rows keep their DOM nodes and their `NodeRef`s are already populated.
- **Direction never rests on colour alone.** Gain/loss uses `fmt_signed_money` (explicit `+`/`-`) *and* switches the label between "Projected growth" and "Projected loss". The green/red is a third, redundant cue.
- **The chart is a `role="slider"`, not a hover tooltip.** `aria-valuetext` carries the readout; arrows step a month, PageUp/Down a year, Home/End the ends. The visible `.chart-readout` mirrors it but is `aria-hidden` so the value is announced once, not twice.
- **Accessible names must contain the visible label** (WCAG 2.5.3). The remove button reads "Remove Global Equity Fund" while showing "Remove"; that's fine, but an `aria-label` that *replaces* rather than extends visible text breaks voice control.
- **Both themes must pass AA.** Check each token against the surface it actually sits on (`--panel` vs `--panel-2` vs `--bg`), not against white or black.
- **Hit targets** are enlarged with a centred `::after` overlay, so the pointer target reaches 44px without changing the drawn control or the grid row height.

## Build & run

**There is no Rust toolchain on the dev machine** — `cargo` and `rustc` are not on PATH, so no bare `cargo` command will run. Docker is installed, and every build and test goes through it. Never tell the user to run `cargo` directly, and never report a change as verified without having run one of the containerised commands below.

The two fast commands share three named volumes (auto-created on first use) holding the cargo registry, the rustup toolchain, and a Linux `target/`. They are what make repeat runs incremental — a *bind-mounted* target dir on this Windows host does not work, cargo recompiles everything every time. Budget ~2 min for the first cold run of each; after that both return in about a second.

- **Compile-check the app** — catches Leptos `view!` macro and type errors without the Trunk/WASM bundling step. This is the command to use while iterating:
  ```bash
  docker run --rm -v "${PWD}:/repo" -v ip-target:/target -v ip-cargo:/usr/local/cargo/registry -v ip-rustup:/usr/local/rustup -w /repo rust:1-slim sh -c "rustup target add wasm32-unknown-unknown && cargo check -p app --target wasm32-unknown-unknown --target-dir /target"
  ```
- **Test the tax crates** (native). `taxkit`'s mock system is behind a feature, so it needs enabling explicitly until `calc` picks it up as a dev-dependency:
  ```bash
  docker run --rm -v "${PWD}:/repo" -v ip-target:/target -v ip-cargo:/usr/local/cargo/registry -w /repo rust:1-slim cargo test -p taxkit -p uk-tax --features taxkit/mock --target-dir /target
  ```
- **Check the jurisdiction boundary.** `taxkit` must not name a country, and `calc` must not depend on `uk-tax`. Both are cheap to verify and easy to regress:
  ```bash
  grep -rniE "isa|sipp|pension|hmrc|scotland|england|£|gbp" taxkit/src --include=*.rs | grep -v "^taxkit/src/mock.rs"
  ```
  ```bash
  docker run --rm -v "${PWD}:/repo" -v ip-cargo:/usr/local/cargo/registry -w /repo rust:1-slim cargo tree -p calc
  ```
  The first should print nothing (`mock.rs` is excluded: it describes a fictional jurisdiction on purpose). The second must not mention `uk-tax`.
- **Test the core** (native, no WASM):
  ```bash
  docker run --rm -v "${PWD}:/repo" -v ip-target:/target -v ip-cargo:/usr/local/cargo/registry -w /repo rust:1-slim cargo test -p calc --target-dir /target
  ```
  Note `--features taxkit/mock`: the fictional tax system `calc` tests against is behind a feature so it never reaches the wasm bundle, which also means a bare `--workspace` silently skips those tests. The CI job passes it too.
  Whole-workspace `cargo test` also runs the pure `app` module tests (`format`, `chart`, `convert`, `outcome`, `goal`, `share`, `model::label_for`, `results::month_at_fraction`); the browser suite below is gated to wasm32 and is skipped here.
- **UI tests** — the headless-browser suite for the `App` component and its children (`app/tests/ui.rs`): mounts the real `<App/>`, drives it with `input`/`change`/`keydown` events, and asserts on rendered text + ARIA. Runs in a dedicated image (Rust + firefox-esr + geckodriver + a `wasm-bindgen-test-runner` pinned to match `wasm-bindgen`), built once then reused:
  ```bash
  docker build -f test.Dockerfile -t ip-wasm-test .
  ```
  ```bash
  docker run --rm -v "${PWD}:/repo" -v ip-target:/target -v ip-cargo:/usr/local/cargo/registry -w /repo ip-wasm-test cargo test -p app --target wasm32-unknown-unknown --test ui --target-dir /target
  ```
- **Run the whole app** (Trunk build → nginx at http://localhost:8080):
  ```bash
  docker compose up --build
  ```
  `docker compose build` on its own is the end-to-end check — it runs the Dockerfile's `trunk build --release` over both crates. Roughly 7s for a source-change rebuild thanks to the Dockerfile's cache mounts (see gotchas); budget several minutes the first time on a machine with a cold BuildKit cache.
- **Dev loop** (needs Rust + `wasm32-unknown-unknown` target + Trunk, e.g. the `.devcontainer`): `./dev.sh` runs `trunk serve` with live reload on :8080. It `cd`s into `app/` first — see the Trunk gotcha below.
- Inside the devcontainer, or on any machine that does have the toolchain, the bare commands work directly: `cargo test -p calc`, whole-workspace `cargo test`, and `cargo build --target wasm32-unknown-unknown --release` from the workspace root as a fast compile check.
- **Deploy** is automatic: every push to `main` runs `.github/workflows/deploy.yml`, which gates on **both** the native `cargo test --workspace` job and the headless `ui` job (`cargo test -p app --target wasm32-unknown-unknown --test ui`, using the runner's preinstalled Firefox/geckodriver via `$GECKOWEBDRIVER`) and then builds with Trunk and publishes to GitHub Pages (`https://<user>.github.io/investment-projection/`). The `TRUNK_VERSION` there must be kept in step with the `Dockerfile` and `.devcontainer/devcontainer.json` pin (`0.21.14`). This is a separate build path from the `Dockerfile`/nginx one, which stays as the local run.

`target/` (workspace-root, shared by both crates) and `app/dist/` are build output (git- and docker-ignored). Trunk emits a self-contained `dist/` (hashed `.js`/`.wasm`/`.css` + `index.html`); nginx serves it. The page must be served over `http://` — a `file://` load won't fetch the WASM.


## Skills

- **`.claude/skills/update-tax-rules/`** — refreshes the figures in `uk-tax/src/tables.rs` against current published sources and stamps them with today's date. It is deliberately scoped to the tables: `engine.rs` is off-limits to it, and anything needing a change there (a new *kind* of taxation, a structural rule the fields cannot express) is reported for a decision rather than implemented. Invoke it when the tax year turns over, or when the app starts showing its stale-figures warning.
## Gotchas & conventions

- **GitHub Pages serves from a subpath, so the Pages build needs `--public-url`.** Trunk's default output references its hashed assets with root-absolute paths (`/app-<hash>.wasm`), which 404 under `https://<user>.github.io/investment-projection/`. The deploy workflow builds with `trunk build --release --public-url ./` to make those references relative; this is safe because there is no router (single `mount_to_body`, no deep links). The local Dockerfile/nginx build serves from `/`, so it deliberately omits the flag. If a future Trunk normalises `./` back to `/`, switch the workflow to the explicit `--public-url /investment-projection/`.
- **Trunk must run from inside `app/`** (both `dev.sh` and the Dockerfile `cd` there). In a virtual workspace `cargo metadata` only resolves a root package when invoked from within the member crate; run from the workspace root, Trunk fails with "could not find the root package of the target crate". The web entry (`index.html`/`styles.css`) therefore lives in `app/`, not at the repo root.
- **Adding anything that computes/derives/rounds/validates a number goes in `calc/src/lib.rs`, returning a `Decimal`** (or an error), and `app/src/main.rs` formats it. Do not reach for `f64` or JS-style number handling in the UI.
- After changing `calc`, add or update a unit test in its `#[cfg(test)] mod tests` — the core is the one part with the densest coverage; keep it that way. `format.rs` and `chart.rs` carry their own tests too. The reactive/DOM layer (`app.rs`, `summary.rs`, `results.rs`, `panel.rs`, `model.rs`) is covered by the headless-browser suite in `app/tests/ui.rs` — when you change a documented UI contract there (the `.stale` shell, focus-on-remove, the error `aria-*` wiring, the shared horizon node, the mode-scoped goal selects, `bind_value`, the scrubber keys), add or update the matching `#[wasm_bindgen_test]`.
- **The two-phase model rests on invariants with no compile-time guard — each is pinned by a named test, don't "simplify" them away.** (1) *Deposits stop at the handover*: `contributions_series` is flat from `horizon_months` on. (2) *The handover is exactly the accumulation projection*: `handover_total` equals a plain deposits run's `projected_total` over the same horizon, to the penny (this is what lets the app avoid stitching series). (3) *`Solution::Depletes(m)` is drawdown months, `depletion_month` is absolute* — they differ by `horizon_months`; "correcting" `describe` to add the accumulation period back would double every answer. (4) *Every apportionment's residue lands on the last member of the group it apportions* so per-row withdrawals sum exactly to `withdrawn_total` — under `ProRata` the group is the whole portfolio, under an ordered strategy it is one account kind. (5) The reconciliation identity `projected = current + contributed − withdrawn + growth` must hold **across** the handover, with `withdrawn` **gross**. (6) *Allowances reset only at a period boundary* and the ledger telescopes: slicing a period's withdrawal into months cannot change its tax. (7) *`gross == net + tax`* pointwise on the rounded series, per row, and in total. (8) *An ordered strategy delivers the net asked for* while the pot lasts. (9) ***`ProRata` is byte-identical* with and without a tax context** — it never opens a session, so this is structural rather than a promise. (10) *The residue rule generalises* to every strategy. (11) *`PreserveGrowth` needs no tax system* — it orders by return, so it is legal on an untaxed projection. (12) *`RateCapped` honours the cap or reports `rate_cap_breached`*, and when it breaches it still delivers the income in full. (13) *Portfolio depletion is the last holding to empty.* Invariants 6–13 are pinned against `taxkit`'s **mock** tax system, not real UK figures, so an April rate change cannot break `calc`.
- **Input parsing is deliberately lenient and must stay non-guessing.** `parse_number` strips whitespace, grouping separators, currency symbols and a stray `%`; anything that is not a plain decimal afterwards still errors (`1.2.3`, `--5`). Note the en-GB assumption: `,` is a thousands separator, never a decimal point.
- **The Dockerfile's `trunk build` uses three BuildKit cache mounts** — the cargo registry, `/src/target`, and `/root/.cache` — which together keep `docker compose build` at ~7s instead of ~59s. `/root/.cache` is the non-obvious one: without it Trunk re-downloads `wasm-bindgen` and `wasm-opt` on every build, which alone was ~16s. They need the `# syntax=docker/dockerfile:1` header — don't drop it. `.dockerignore` excluding `target/` is correct and should stay: the host's `target/` holds Windows-native artifacts that are useless to the Linux build. Cache mounts are the fix, not un-ignoring it.
- **The devcontainer `dev.sh` path (Trunk live-reload) has two host-specific traps.** (1) `trunk serve` must bind `--address 0.0.0.0`, not its `127.0.0.1` default — bound to loopback it's only reachable inside the container, so VS Code's forwarded 8080 (and any host browser) gets nothing. (2) `CARGO_TARGET_DIR` is set to `/home/vscode/target` (container-local, `vscode`-owned) in `devcontainer.json`. Do **not** let cargo/Trunk build into the bind-mounted `target/`: the host dir's files can be root-owned, so the build dies with `failed to open .../target/debug/.cargo-build-lock: Permission denied (os error 13)` → `cargo build ... exit status: 101` → Trunk serves an empty `dist/` and every request 404s (the server still *listens*, so it looks like a networking bug but isn't). The bind-mounted target is also why cargo recompiled everything each run. If a stale root-owned `target/` predates this fix, `sudo chown -R vscode:vscode target` (or `rm -rf target`) unblocks it.
- **Breakpoint debugging works on `calc`, not `app`.** `.vscode/launch.json` has two CodeLLDB (`vadimcn.vscode-lldb`) configs that build and launch the `calc` unit-test binary natively — set a breakpoint in a `calc` test and step through the `Decimal` math. `app` is Rust→WASM in the browser, so there's no native process to attach lldb to; since `app` only formats what `calc` returns, reproduce any wrong number in a `calc` test and debug it there. (Genuine UI/reactive-layer bugs are browser-devtools/Chrome-DWARF territory, a heavier host-side setup that isn't wired into the devcontainer.) Debug builds honour `CARGO_TARGET_DIR`, so CodeLLDB finds the binary with no extra path config.
- `nginx.conf` relies on nginx's bundled `mime.types` and only overrides `.wasm` via a `location` block — don't replace the whole `types {}` map.
- The chart is a hand-built SVG string in `chart.rs` (`chart_svg`) set via `inner_html`; its colours reference the CSS custom properties (`var(--accent)` etc.) from `styles.css` because the SVG is in the live DOM. Keep the palette in `styles.css`, not duplicated in Rust — that is also what makes the light theme work for free, since `@media (prefers-color-scheme: light)` just redefines the same tokens.
- **The chart's label size is coupled to its rendered width.** Text is sized in viewBox units, so what the reader sees is `AXIS_FONT * width / 640`. `AXIS_FONT` (chart.rs) and `.chart-stage`'s `min-width`/`max-width` (styles.css) must be changed together, or the labels shrink below legibility (they were 8px on a phone) or balloon. The gutters `PL`/`PR` are sized against `AXIS_FONT` too, and `fmt_axis` abbreviates past a million so a long label can't outgrow `PL`. The drawdown **handover divider** (`chart_svg`'s `handover` arg) renders its `"drawdown"` label at the same `AXIS_FONT`, so keep it one short word — do *not* shrink `AXIS_FONT` to fit a longer one (that shrinks the axis labels too). The handover month also *replaces* the nearest x-axis tick rather than adding one, so labels can't collide; the y-axis is floored at £0 (`min_v = 0`) so a drawdown to nothing reads as reaching the floor.
- **The chart scrubber positions itself from `PLOT_*_FRAC`**, exported by `chart.rs` from the same viewBox constants the line is drawn with. Don't hard-code those percentages in CSS — the marker would drift off the data.
- **A `@media` block adds no specificity, so source order decides.** `styles.css` keeps its desktop overrides *after* the base rule they override. `.periods { margin-top: auto }` sits in a second `@media (min-width: 960px)` block placed below the base `.periods` rule for exactly this reason — moved up next to the other desktop rules, the later `margin-top: 22px` silently wins and the control stops pinning to the panel foot. Same trap applies to `.field-invalid:focus`, which needs to outrank `input:focus`. The summary's tablet-band rule sidesteps it entirely: `.stat-accent:nth-last-child(6) ~ .stat` cannot match the headline at all, so it does not depend on out-ordering `.stat-accent` the way a bare `.stat` would.
- **A `<select>` whose *options* come from the tax system is still a static option set.** The account picker on each row is built by iterating `TAX_SYSTEM.account_kinds()`, which is fixed for a build — so the "never swap a select's options reactively" rule is not violated. What *is* reactive is the cost-basis input beside it, which appears when the selected kind's `needs_cost_basis` is set. Drive the select with `<option selected=…>`, never `prop:value`.
- **`TaxContext` cannot derive `PartialEq`.** It holds a `&'static dyn TaxSystem`, and a trait object's address is not a reliable identity — implementations are zero-sized, so distinct ones can share one, and comparing vtable pointers is unreliable across codegen units. The hand-written impl compares `label()` and `rules_label()` instead, which is stable and enough for the memo's change detection.
- **Drawdown mode drops the aligned row grid on purpose.** The row gains an account picker and sometimes a cost box — seven fields where the five-track desktop template already needed a px floor on the rate track. Rather than squeeze two more columns in, `.inv-editor.with-accounts` falls back to the labelled-card layout the mobile breakpoint already uses, and the shared `.inv-head` is hidden because it could no longer describe the columns. Don't "restore" the header there.
- **`app` names a jurisdiction on exactly one line**: `convert::TAX_SYSTEM`. Every account option, region option, conventional order, currency symbol and freshness judgement is asked of that. If you find yourself matching on an account id or writing `£` in the UI, push it behind the trait instead.
- **`calc` names no currency either.** Money in `calc`'s own error messages (the goal-seek "can't reach £X" lines) is formatted with the symbol carried on `CalcInput::currency`, which the app fills from `TAX_SYSTEM.currency_symbol()` in *both* modes — a taxed context's symbol takes precedence, and a blank falls back to the neutral `¤` marker. Don't reintroduce a `£` literal in `fmt_money_plain`; thread the caller's symbol through instead. (`calc` still uses `£` freely in *doc comments and this file's prose* — the ban is on emitted strings.)
- **The withdrawal strategies are one catalogue: `convert::StrategyChoice`.** Its five variants own the id (form state + share link), the picker label, the `in_comparison` flag and the `calc::Strategy` constructor; the picker `<select>` iterates `StrategyChoice::ALL`, `strategy_from` is a thin `from_id(id).build(cap)`, and `strategy::candidates()` is the `in_comparison` subset. The comparison's *row* label is derived from the built `Strategy` by `strategy::strategy_label` (keyed off `Order`/`Limit`, like `strategy_hint`), not written beside it — so picker and row wording stay deliberately different without a second list to keep in sync. Adding a strategy is a new variant; the `match self` methods then fail to compile until every site handles it. Don't reintroduce free-standing `STRATEGY_*` id consts.
- **The clock is read in `app`, never in `calc`.** `freshness::today()` is the only clock read; a projection must stay a pure function of the form, or the same shared link would produce different numbers depending on when it was opened and the browser suite would start failing on a date. Staleness never feeds back into the arithmetic.
- **Never round inside a tax walk.** `taxkit::ladder` carries full-precision `Decimal` and the caller rounds once at its own output boundary, matching `calc`'s existing discipline. Rounding a grossed-up withdrawal to the penny per account per month looks harmless and accumulates a systematic drift over hundreds of months. One consequence to expect: where a rung's keep is not exactly representable (0.6, say), the delivered net can fall an attopenny short of the requested net — compare rounded figures, never raw ones. `Draw::net` is derived as `gross - tax` rather than accumulated, so that identity at least is exact by construction.
- **A marginal-rate effect must be expressed as a rung, not computed as an adjustment.** The UK personal allowance is withdrawn above £100,000, making the true marginal rate 60% in that stretch. Computing that as a correction is circular with grossing up — you need the total before you can work out the allowance that determines the total. `uk_tax::engine` flattens it into an extra 60% rung instead: algebraically identical, monotone, and no special case in the walker. The same flattening is what makes Scotland's six bands need no code at all, only a longer slice.
- **A rate update edits `uk-tax/src/tables.rs` and nothing else.** Add a *new* `TaxYear` const and prepend it to `TAX_YEARS`; do not edit an existing one, since old tables cost nothing and are the only record of what the figures used to be. Set `as_of` to the day you checked and put the URLs actually used in `source_note`. Adding an `AccountKind` is in scope there only when its taxation matches an existing `WithdrawalTax` — a genuinely new mechanism is an `engine.rs` change and a decision, not a table edit.
- **`styles.css` is the single source of the palette for both themes.** `@media (prefers-color-scheme: light)` redefines the same custom properties, which is why the chart's SVG follows along without any Rust change — it references `var(--accent)` etc. from the live DOM. Adding a colour means adding it to *both* blocks.
- **Form controls with a non-default initial value need mount-safe binding, not `prop:value`.** In Leptos's `view!` expansion an element's props are set *before* its children mount, so `prop:value` on a `<select>` runs while its `<option>`s don't exist yet — a non-first initial value (e.g. a horizon-unit defaulting to `"months"`) silently fails to apply and the control falls back to the first option. Drive selects from the options instead: `<option value="months" selected=move || sig.get() == "months">`. Text `<input>`s have the mirror problem (plus a caret-reset) and use the `bind_value` node-ref effect. Default-valued controls appear to work by coincidence because the fallback *is* their value, so test initial rendering with a non-default value. **Never build one `<select>` whose *option set* swaps reactively:** when the browser destroys the selected `<option>` it silently resets the control to its first entry, and re-evaluating `selected=` doesn't re-drive it. The mode-dependent goal picker sidesteps this by rendering **two separate selects, one per mode, each with a static option set** — only the current mode's is in the DOM. (The radio inputs of the mode switch use `prop:checked`, not the `checked` *attribute*: the attribute sets only the initial state, so after a user interaction a reactive `checked=` would not re-drive the DOM. The "props set before children mount" caveat does not apply — a radio `<input>` has no children.)
- **The shareable link lives in the URL *fragment* (`#v=…`), and is read only on a full page load.** `share::encode`/`decode` serialize the whole form (rows, periods, mode, withdrawal, goal) to JSON, base64url-encode it (`base64::URL_SAFE_NO_PAD`, so the payload is a single URL-safe token with no `+`/`/`/`=`), and carry it in the `v` fragment parameter; `App` seeds from it once at mount via `read_hash`, falling back to the built-in example when `decode` returns `None` (it is total — any malformed fragment yields `None`, never an error). The JSON is a versioned envelope (`{"v":2,…}`); a mismatched version decodes to `None` rather than being half-read. **`VERSION` is `2`**: the overhaul bumped it because a v1 link's per-row `mode`/`flow` have no meaning under the new model (an old `"total"` rate or `"withdraw"` flow would be silently mis-read as an annual rate or a deposit), so v1 links are rejected outright and fall back to the example. Prefer a **new `#[serde(default)]` field** over another version bump for future additions — a bump hard-rejects every link already in the wild. The fragment (not a query string) is deliberate: it is never sent in the HTTP request, so a shared link's portfolio data never leaves the page — the "nothing leaves this page" property holds. Two consequences to remember when testing: (1) a fragment-only change to an already-open page does **not** re-run the app, so pasting a different `#v=…` into the same tab won't re-seed — only a real reload or a fresh tab does; (2) "Copy link" writes the fragment with `history.replaceState`, deliberately *not* a hash assignment, so it doesn't pile up Back-button entries. `RowData::id` is `#[serde(skip)]` — positional bookkeeping the codec drops on encode and reassigns by row position on decode, so it never bloats the link. The codec uses `serde_json` + `base64` (both pure Rust) precisely so the module stays free of `web_sys` and its round-trip is natively testable; don't reach for `btoa`/`atob` or `js_sys`.
- **Devcontainer `trunk serve` does not see host-side file edits.** The `notify` watcher relies on inotify, which doesn't fire for writes made on the Windows host against the bind-mounted source — so editing files from the host (rather than inside the container) leaves the running server serving a stale `dist/`, and even `touch` from inside the container may not wake it. After host edits, restart the server from inside the container (`pkill -f 'trunk serve'` then relaunch the `dev.sh` command) to force a fresh build; watch `/tmp/trunk.log` (if you redirect there) for `INFO success`.
- Leptos 0.6, stable Rust idioms (`.get()`/`.set()`, not the nightly call sugar). Pin/verify the Leptos version before using newer-version APIs.
- **The UI suite (`app/tests/ui.rs`) has three environment traps.** (1) **`wasm-bindgen-test-runner` must match the `wasm-bindgen` version in `Cargo.lock` exactly**, or it rejects the module with a schema-version error — both `test.Dockerfile` and the CI `ui` job derive the version from `Cargo.lock` rather than hard-coding it, so a `cargo update` can't silently desync them. (2) **Leptos 0.6 has no `tick()`** — the harness's `settle()` flushes reactive effects by awaiting a resolved promise twice (an effect can queue another). Mount-time effects are microtasks, so a test that reads a *seeded text input's* value (or places a caret in it) must `settle().await` first; rendered figures and `selected=`-driven `<select>`s appear synchronously and need no settle. (3) **The wasm-bindgen test page loads no CSS** — `mount_with` injects `styles.css` once via `include_str!`, without which `client_width()` is 0 and the scrubber's pixel maths can't run. Tests mount the real `<App/>` seeded through `share::encode` (so the `#v=` load path is exercised too) and query within the returned root, never `document`, because earlier tests' mounts stay in the page. `set_bubbles(true)` on every synthetic event is required — Leptos delegates events at the root, so a non-bubbling event never reaches the handler.
